# Development Workflow

## Work Tiers

Choose the lightest tier that fits. When unsure, use the heavier one. `BOOTSTRAPPER_SPEC.md` may name this project's examples of each tier.

| Tier | Covers | Branch and PR | Depth |
|---|---|---|---|
| Ops/data | One-off operational scripts and data entry. Touches no application code, tests, CI, dependencies, or config. | Commit to the default branch. No PR. | Dry run first, then read back the result. |
| Small change | A contained fix or tweak. No API contract, schema, auth, or dependency change. | One branch, one PR, opened when the work is ready. | Gates A and B, proportionate to the change. |
| Feature | A new feature; an API contract, schema, auth or permission, dependency, or shared-utility change; anything that spans sessions. | A branch, plus a draft PR at the first commit. | Gates A and B in full, plus the full review in `code-review.md`. |

## Version Control

1. Start from the current default branch: fetch, then branch from its tip. Branch from another unmerged branch only when the work depends on it, and say so in the PR.
2. One PR per piece of work, not per edit. Follow-up edits to work whose PR is still open go on that branch. Related small changes from the same session share one branch and one PR.
3. One commit per logical step, together with its tests. Each commit leaves the suite in the state that step expects: green, or deliberately red only for a documented test-first step that the next commit turns green.
4. Commit messages say what changed and why, including rejected alternatives and any defect a test was shown to catch.
5. Push when a step is complete, so an interrupted session loses at most one step.
6. Never force-push a branch under review unless the human asks. A rejected push means the remote moved: investigate, do not overwrite.
7. When an open PR conflicts with the default branch, bring the default branch in and resolve both sides. Never discard either side to make the conflict go away.
8. Never merge a pull request. Opening it, updating it, and reporting that it is ready is the agent's job; merging is the human's.
9. No agent attribution anywhere: no `Co-Authored-By` trailers, no "generated with" footers, no agent names in commits, PR titles or bodies, branch names, code comments, or docs.
10. Clean up after yourself: remove the worktrees and local branches you created once their work has merged.

## Gate A: Before Changing Code

1. Trace the execution paths the change touches.
2. List the files to change and everything that depends on them.
3. For a change that crosses layers, list each hop: route, storage or model output, API wrapper, consumer, and where the result is displayed.
4. List the edge cases that apply (see `code-review.md`).

## Gate B: Before Calling It Done

1. Re-trace the changed paths end to end. Confirm imports and signatures.
2. Where an old code path was replaced, confirm existing data and legacy behavior still work.
3. Run the tests (see Verification).
4. For UI changes, exercise the affected pages in a running app. If that was not possible, say so explicitly.
5. Feature tier: run the full review in `code-review.md`.
6. Record what was verified, and how, in the plan doc.

## Verification

- While iterating, run the tests that cover the change.
- Run the full suite once before pushing, and again only if code changed afterwards. CI is the final gate.
- Report results from actual output. Never claim a pass that was not observed.

## Cross-Client Parity

- A backend or contract change is incomplete until every consumer (GUI, API client, companion app) is updated, or the omission is recorded in the plan doc.
- When one shared UI or runtime surface changes, review its counterpart in the same task unless the change is explicitly scoped to one surface.

## Abstraction

- Create seams where replacement is likely: providers, transport, storage, runtime controllers, platform adapters.
- Prefer cohesive classes or focused modules for stateful, lifecycle-heavy logic, and composition over inheritance.
- Keep platform shells thin; move shared behavior into neutral shared modules.
- Every new abstraction must earn its place through replaceability, testability, or platform separation. No speculative wrappers.
- When a new seam replaces old code paths, move every caller, or record the staged migration in the plan doc.

## Plans

`plans/` is the only planning workspace and the durable record of what changed and why.

1. Every PR and every ops/data task gets exactly one new file, `plans/YYYY-MM-DD-short-name.md`, created from `plans/IMPLEMENTATION_TEMPLATE.md` (`scripts/create-implementation-doc.sh YYYY-MM-DD short-name`).
2. The doc describes itself. Its header carries `Status`, `Category`, and a one-line plain-language `Summary`. There is no index or monthly file to update, so two branches never edit the same plans file.
3. Create it with `Status: in-progress` in the first commit. Before asking for review, set the final status (`implemented-verified`, `partial`, or `not-implemented`) and fill in Verification.
4. Keep it a record, not a transcript: the request, what changed and why, files and integration points, edge cases and risks, verification commands with their results, and follow-ups. Do not paste the chat plan or restate the diff.
5. Later edits to the same work update its doc. Docs for finished work are history: append corrections, never rewrite or delete.
6. A change without its plan doc is incomplete. Run `scripts/verify-plans-workflow.sh` before pushing.
7. `plans/INDEX.md` and `plans/YYYY-MM.md`, where they exist, are frozen history from the previous workflow. Do not add to them.
8. Ideas and reference material that are not yet work go in `plans/IDEAS.md`.

## Context Discipline

- One task per session where possible. Plan docs and git history carry context between sessions, so a fresh session loses nothing. When an unrelated task starts in a long-running session, say once that a fresh session would be cheaper.
- Read files in the ranges needed, not wholesale. Search by keyword before opening.

# Code Review

## When The Full Review Runs

- Feature-tier work, before the PR is marked ready.
- Whenever the human asks for a review.

A full review checks every file in scope against every dimension below, tiers the findings (Critical / High / Moderate / Low), and records them in the plan doc. A small change gets the same questions applied to the lines it touches, not a sweep of the codebase.

## Review Dimensions

### Resource Efficiency
- No unnecessary allocations, copies, or repeated computation in hot paths.
- Pools, executors, and caches are bounded and cleaned up on shutdown.
- No unbounded growth of collections in long-running loops or streams.
- Temporary files and scratch storage have cleanup or a TTL.

### Speed
- No blocking I/O on an event loop, a request hot path, or a UI thread.
- Every network call, subprocess call, and blocking wait has an explicit timeout.
- Sequential operations that could run concurrently are flagged.
- No unnecessary serialization round-trips and no N+1 queries.
- Startup paths warm the resources the first request needs.

### Concurrency
- Shared mutable state is protected by the mechanism the runtime provides: a lock, a transaction, or a single-writer queue.
- Check-then-act on shared state is atomic.
- No lock is held across an await, blocking I/O, or a sleep.
- Background workers can be stopped cleanly and do not block process exit.
- No fire-and-forget async work: results are awaited, stored, or given an error handler.
- No time-of-check/time-of-use races on the file system, the database, or state transitions.

### Memory And Handles
- Streams, file handles, connections, and subprocesses are closed on every path, including errors.
- Caches and registries have eviction.
- Cancelled or timed-out work leaves no orphaned references, timers, or listeners.
- Closures do not hold large objects past their useful life.

### Edge Cases
- Null, undefined, or missing on every input, return value, and optional field.
- Empty collections, strings, and buffers.
- Boundary values: zero, negative, maximum, a single element.
- Error returns from external services: 4xx and 5xx, connection refused, DNS failure, timeout.
- Malformed input: invalid JSON, unexpected content type, oversized payload, truncated stream.
- Concurrent use: two requests for the same resource, rapid connect and disconnect, double close.

### Error Handling
- No catch-all that swallows cancellation, interrupts, or errors it cannot handle.
- Every external call (network, file, subprocess, database) handles failure and logs it.
- Error messages say what was attempted, on which resource, with what input.
- No silent failure: returning a default without logging is a finding.
- Retry loops have a maximum attempt count.

### Security
- No string-built queries or commands: SQL, NoSQL, or shell.
- No unvalidated user input in subprocess arguments, file paths, or dynamic evaluation.
- Auth and signature checks use constant-time comparison.
- Uploads are checked for size and content type.
- No secrets in logs, error messages, or responses.

### Contract Consistency
- Signatures match between caller and callee across module boundaries.
- Every environment variable the code reads appears in `.env.example` and the deploy templates, with sensitive values redacted.
- Service names and ports in container or deploy config match the real ones.
- API route paths and methods match what clients call.

# Coding Standards

Write in the language, style, and idioms the repository already uses. Language-specific conventions belong in `BOOTSTRAPPER_SPEC.md`; the rules below apply in any language.

- Clear names, explicit error handling, minimal side effects.
- Validate input at system boundaries: user input, external APIs, files. Trust internal code and framework guarantees.
- No dead code, and no unused imports or dependencies.
- Read and write text files with an explicit encoding: UTF-8 unless the format says otherwise.
- Release files, connections, and other handles on every path, using the language's scoped-cleanup construct.
- Give every network request, subprocess, and blocking wait a timeout.
- Never run blocking work on a UI thread or an event loop.
- Loops that wait or retry have an exit condition and an attempt limit.
- Synchronize shared mutable state. Make check-then-act atomic. Hold no lock across a blocking call.
- Background work has a top-level error handler that logs, and can be stopped cleanly.
- Never swallow an error silently. Log what was attempted, on which resource, with what input.
- Copy nested data before mutating it when the caller must not see the change. No shared mutable default arguments.
- Comments explain why, not what.

# Technology Stack

- Stack facts (languages, frameworks, commands, deploy target) live in `BOOTSTRAPPER_SPEC.md`. Setup and operator steps live in `README.md`.
- Prefer the patterns and libraries already in the repo. Add a dependency only when it clearly beats what exists. When replacing one, trace every use of the old one.
- Before adding or upgrading a dependency, check its current documentation instead of relying on memory.
- Centralize API wrappers and shared transformations. Keep route handlers thin and integration points explicit.
- Background services, pollers, and helper daemons stay resource-conscious: minimal idle memory, polling no tighter than needed, cached or event-driven data over long-lived heavy processes, and no agent CLI left running when an on-demand read would do.
- Do not delete, move, or gitignore the governance files (`.cursor/`, `.claude/rules/`, `.codex/`, `rulesets/`, `plans/`, `scripts/`) on your own. Whether a repo tracks them or keeps them local is the owner's decision.

# Sandbox And Safety

- Prefer non-destructive exploration commands.
- Never print or persist secrets from env or config files.
- Scope searches to source directories. Exclude dependency, build, version-control, and worktree directories (`node_modules`, `dist`, `.git`, `.claude/worktrees`, virtualenvs).
